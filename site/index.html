Encrypted secrets

kvage keeps key value pairs in a YAML file with every value encrypted with age. Type your passphrase once per session, share the store through git, and load project variables when you enter a directory.

From an empty machine to a masked list of secrets

Create a passphrase protected key, save a value at a prompt that does not echo, and read it back. list never prints full values unless you ask for them.

A masked value shows two characters at each end around a mask of fixed width, so it does not reveal the length. Short values show less, and values under four characters show nothing.

bash
# create a passphrase-protected key
$ kvage vault init

# prompted, no echo
$ kvage set db_password
$ kvage set pin

$ kvage list
db_password: s3****et
pin: ****

# forget the key and stop the agent
$ kvage lock

Small commands that keep secrets off your screen and out of your history

  • Masked listing

    kvage list shows every key with its value masked. Add --reveal only when you want the full values.

  • Prompted input

    kvage set name asks for the value without echo, or reads it from stdin. Nothing is left in your shell history.

  • Search by name or value

    Match key names as a substring or a glob with no decryption. search --value asks for the text at a prompt and lists matches masked.

  • Standard age files

    Every value is a standard age file inside plain YAML. Anything kvage writes can be read with age itself.

  • A store per project

    A .kvage/ directory gives a project its own store, key and recipients. Only the current directory is checked, never its parents.

  • Export to the environment

    kvage export prints export NAME='value' lines, with a filter when you only need a few.

  • No guessing which file

    kvage status shows which store, key and recipients are in use and why, plus the session state.

  • One static binary

    Written in Go and released as a single binary for Linux, macOS and Windows. Download it and run it.

For teams

Commit the store to git and let the whole team read it

Put a public-keys.txt next to the store with one age public key per line. From then on every value is encrypted for everyone listed, and the store can be committed to git together with the list, as with SOPS.

  • Writing needs no private key. set encrypts for the listed recipients without unlocking anything.
  • One command after the list changes. kvage rekey encrypts the existing values again for the current recipients, and writes nothing unless every value could be decrypted.
  • Your personal store stays yours. The recipients list always comes from the directory of the store being written, so entering a project cannot change who your own values are encrypted for.

Removing someone from the list does not take back what they could already read. When someone must lose access, change the secrets themselves.

public-keys.txt
# team
age1qy...   # alice
age1zx...   # bob
bash
$ kvage rekey            # the store
$ kvage rekey --rc       # the store and ./.kvagerc

For agents and automation

Give coding agents and scripts the credentials they need, and nothing to execute

You unlock once. The tools you start after that read what they need through the same commands you use, and a project file can only ever hand them variables.

  • One passphrase per session

    The first command that needs the key asks for the passphrase and starts a background agent that decrypts for later commands. The passphrase is always asked on the terminal, never read from stdin, so pipes keep working.

  • Variables on cd, never code

    An encrypted .kvagerc exports its variables when you enter the directory. The decrypted text is never given to the shell: kvage parses it and emits only export NAME='value' lines.

  • Nothing in argv or history

    Values come from a prompt or from stdin, for example pass show db | kvage set db_password. Passing a value as an argument works, and kvage warns you about it.

What a .kvagerc cannot do

age does not authenticate who encrypted a file, so anyone who knows your public key can create a .kvagerc that decrypts correctly. kvage treats the file as untrusted for that reason.

  • Command substitution, pipes, redirections, alias, functions and source are ignored, with a warning that names the line but never its content.
  • Variables that change how programs are found or loaded are not set: PATH, LD_*, DYLD_*, BASH_ENV, NODE_OPTIONS, PYTHONPATH, GIT_SSH* and more, unless you allow them in your own config.
  • With the key locked, the hook does not prompt on every cd. It prints one line and loads nothing.
  • Errors go to stderr and the command exits with a failure status, so scripts can stop.
bash
$ cat > env.txt <<'END'
export API_HOST="api.example.com"
export API_TOKEN='s3cret'
CACHE_DIR=$HOME/.cache/myapp
END
$ kvage encrypt < env.txt > .kvagerc && rm env.txt
$ echo 'eval "$(kvage shellrc)"' >> ~/.bashrc

Be clear about what an open session means: programs you run, agents included, can read your secrets by running kvage get. Use kvage lock, an inactivity timeout, or session.mode: always when that matters.

How the key is protected

Three layers between your private key and a copied file

  1. At rest

    A passphrase on the key file

    kvage vault init encrypts your age identity with a passphrase, in the standard age format. If you already have a key it is protected in place, with the same public key and nothing to encrypt again.

    • A copy of the file is useless without the passphrase.
    • age -d -i key.txt file.age works with it.
    • Copy it to another machine and use it there.
  2. In use

    A session agent that holds the key

    unlock, lock and status control a background agent that keeps the key in memory, never on disk in the clear. The session ends on lock, logout, reboot or an optional inactivity timeout.

    • On Linux other programs of your user cannot ptrace it or read its memory.
    • No core dumps, and memory kept out of swap when the system limit allows it.
    • It answers only your user, and only the kvage executable.
  3. Linux with TPM 2.0

    Sessions guarded by the TPM

    While a session is open the unlocked key is sealed in the machine's TPM 2.0 and only materialises in memory for the milliseconds each command needs.

    • A memory image (hibernation, swap, crash dump) does not contain the key.
    • The session ends on reboot and on hibernation; it costs one TPM operation per command.
    • The limits below still apply to root and to your own programs.

Sessions exist on Linux and macOS. On macOS the agent checks only the user and applies no memory protection. On Windows the passphrase is asked for on every command.

Honest limits

What it does not protect against

kvage protects secrets at rest: a copy of the store, of a .kvagerc or of a passphrase protected key file is useless without the passphrase. These are the cases it does not cover.

  • root

    root can read the agent's memory and take the key, capture your passphrase as you type it, or read values as they are decrypted. Nothing in kvage defends against a compromised root or kernel.

  • Other programs of your own user while a session is open

    They cannot talk to the agent directly, but nothing stops them from running kvage get themselves. An open session means that programs you run can read your secrets.

  • Memory images of an ordinary session

    Locking means ending the agent process. Without the TPM guard, the memory of a hibernated machine, a crash dump or a VM snapshot taken while a session was open may contain the key.

  • What you print or type in the clear

    get, export and list --reveal print secrets that stay in your scrollback. A value passed as an argument stays in your shell history and is briefly visible in the process list.

  • A forgotten passphrase or an old plain key

    There is no recovery for a forgotten passphrase. Protecting a key in place does not erase older copies of the plain file, so if it may have leaked, protect a new key and rekey.

  • Access someone already had

    A removed recipient may have kept a copy of the store, and git keeps history. Change the secrets themselves.

Quick start

From download to first secret in three steps

  1. 1

    Get the binary

    Download the binary for your platform from the releases page, or build it from source with Go 1.26 or newer.

    $ go build -o kvage ./src
  2. 2

    Create a protected key

    kvage asks for a new passphrase twice and stores the key in its config directory.

    $ kvage vault init
  3. 3

    Store and read a secret

    The value is asked for without echo. Listing keeps it masked.

    $ kvage set github_token
$ kvage get github_token
$ kvage list

Questions people ask before trusting a secrets tool

Can I read my secrets without kvage?

Yes. Values are standard age files and a protected key is a standard age identity encrypted with a passphrase, so age can decrypt both.

What happens if I forget the passphrase?

There is no recovery. Keep the passphrase somewhere you trust.

Can a .kvagerc from a repository run code on my machine?

No. kvage parses the decrypted file and gives the shell only export NAME='value' lines. Commands, aliases and functions are ignored, and variables such as PATH or LD_* are not set unless you allow them in your own config.

How do I remove a teammate?

Delete their line from public-keys.txt and run kvage rekey. They may have kept a copy of the store, and git keeps history, so also change the secrets they could read.

Does it work on Windows and macOS?

Yes, with differences. Sessions exist on Linux and macOS, and the memory protections of the agent apply on Linux only. On Windows the passphrase is asked for on every command.

Do I have to protect my key with a passphrase?

No. A plain key file keeps working, and kvage reminds you to protect it when used from a terminal. You can turn that reminder off in config.yaml.

Can I stop the session from staying open all day?

Yes. Set session.timeout to lock after a period without use, or session.mode: always to be asked every time with no agent at all.
